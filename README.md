# VeriSearch

**RL-trained retrieval reasoner with a faithfulness reward.**

A small LLM trained with GRPO to interleave reasoning and retrieval: it decides *when* to
search, *what* to search for, and *when it has enough evidence* to answer. Rewarded on
verifiable correctness, citation faithfulness, and retrieval cost.

> Status: **P0 — setup.** No results yet. Every number in this README will carry a 95%
> bootstrap confidence interval and a W&B run link, or it will not be here.

The full brief and working agreement is [PROJECT.md](PROJECT.md).

## The idea in 60 seconds

Ask *"Which director of the 1999 film that won Best Picture was born in Australia?"*

Normal RAG searches once with the original question and answers. That fails twice over.
It needs two hops — find the film, *then* find the director's birthplace — and the second
query cannot be written until the first one returns. And when the retrieved passages come
back weak, the model fills the gap with a confident guess that no document supports.

VeriSearch trains the loop instead of scripting it:

```
question → think → search → read → think → search → read → answer
```

The model chooses how many loops. The reward has three terms pulling against each other:

| Term | What it measures | Weight |
|---|---|---|
| correctness | token F1 vs gold answer, plus EM bonus | `w_c = 1.0` |
| faithfulness | fraction of atomic claims entailed by *retrieved* passages | `w_a = 0.5` |
| retrieval cost | searches / `SEARCH_BUDGET`, subtracted | `λ` swept |

Faithfulness is the anti-hallucination lever and the part most work skips. Retrieval cost
is the dial: turn it up and the model searches less. Four models trained at four λ values
give an accuracy-vs-retrieval frontier — *how much accuracy does one more search buy?*

## Quickstart

```bash
uv venv --python 3.11
uv pip install -e ".[dev]"
```

Check your machine:

```bash
python scripts/00_setup_check.py
```

Run the same gates Jenkins runs:

```bash
uv run ruff check . && uv run ruff format --check . && uv run mypy --strict verisearch/ && uv run pytest
```

Extras are split so the PR pipeline stays CPU-only and fast:

| Extra | Install for | Who |
|---|---|---|
| `[dev]` | lint, typecheck, test — everything CI runs on a PR | both |
| `[retrieval]` | building the FAISS index, embedding, NLI scorer | Ayesha |
| `[train]` | vLLM rollouts, LoRA, GRPO | Dhrubo, GPU box only |

`uv.lock` is the real pin. Commit it; both machines install from it.

### What this means

**1. This machine cannot train. Three independent walls, one of them permanent.**

| Wall | Measured | Required |
|---|---|---|
| VRAM | 2.0 GB | Qwen2.5-1.5B in bf16 is ~3.0 GB of weights alone — before activations, gradients, KV cache or the reference model |
| Compute capability | 6.1 (Pascal) | bf16 needs ≥ 8.0 (Ampere); FlashAttention-2 needs ≥ 8.0 |
| Driver | 511.69 (CUDA 11.6) | torch `cu121` wheels want ≥ 527 |

The driver is a download. The dtype is a fallback to fp16. **2.0 GB is neither.** GRPO at
`group_size: 8` holds eight concurrent rollouts with a context that grows every turn, plus
LoRA gradients, plus a frozen reference model for the KL term. The gap is an order of
magnitude, not a tuning parameter. 4-bit NF4, gradient checkpointing and `group_size: 2`
together do not close it, and each one damages the experiment we are running.

**No local training. This is settled by measurement, not preference.**

**2. What this does not block.** Most of Ayesha's 70% is CPU work and starts today:

| Component | Runs here? |
|---|---|
| `types.py`, `config.py`, CI, tests | Yes |
| Corpus prep, chunking, dataset splits | Yes |
| `bge-small` embedding of the corpus | Yes — slow (hours, batched), but it completes |
| FAISS HNSW build and search | Yes — see RAM note below |
| NLI faithfulness scoring (offline, batched) | Yes — slow, and it is offline by design |
| Baselines 1, 2, 3 (no training) | Yes, against a hosted or small local model |
| Fake `Retriever` / fake trajectories | Yes |
| GRPO training, 1.5B or 3B | **No** |
| Baseline 4 (SFT) | **No** |
| vLLM serving | **No** — vLLM preallocates VRAM |

Dhrubo's P1 spike (evaluating the three multi-turn RL routes) is also unblocked: it is a
reading-and-API exercise, not a training run.

**3. The GPU is an open decision, and it is the top project risk.** Options, cheapest first:

| Option | Cost | Notes |
|---|---|---|
| Dhrubo's machine | Free | RTX 5060 Ti 16 GB (Blackwell, cc 12.0), driver 580.173.02, torch 2.13.0+cu130, `RESULT: PASS`. 1.5B at group 8 fits; 3B at bf16 does not alongside vLLM. The index, the NLI scorer, baselines, training, the sweep and serving all run here. |
| Kaggle Notebooks | Free, 30 h/week | 2× T4 16 GB. Turing (7.5): fp16 only, no FA2. Enough for 1.5B. 12 h session cap and no persistent disk — needs checkpoint-to-cloud |
| Rented GPU (Vast.ai / RunPod) | ~$0.3–0.5/h | 4090 24 GB or A40 48 GB. bf16 and FA2 both work. The four-run λ sweep on 3B is the real bill — estimate it before committing |
| University cluster | Free if available | Worth one email. Queue latency is the risk |

Decision owner: Ayesha. **Must close before P3 starts.** P1 and P2 do not depend on it.

**4. RAM is tight but workable; disk decides the corpus.** 15.7 GB RAM against a 5M-passage
abstracts corpus: 5M × 384 dims × 4 bytes ≈ 7.7 GB of vectors, plus HNSW graph overhead.
It fits if the index is built in batches. A full paragraph dump (~20M passages, ≈ 32 GB of
vectors) does not fit in either RAM or the 81.4 GB of free disk.

**Corpus decision: HotpotQA Wikipedia abstracts.** Standard for multi-hop QA, aligned with
the training data, and it fits the hardware. Recorded here rather than left open because
there is no real alternative on this machine.

**5. The check's own exit criterion changes.** The earlier version of this section said
"RESULT must read PASS before P1 starts." That is wrong: the GPU gate belongs to whichever
box runs training, not to the laptop that writes the library. `RESULT: FAIL` is the correct
and permanent answer here. Re-run `00_setup_check.py` on the training box once option 3 is
chosen, and record *that* report as the P3 gate.

## Engineering standards

Enforced in CI. A PR violating any of these does not merge.

- `mypy --strict` on the whole package. No bare `Any`.
- `from __future__ import annotations` in every module — enforced by ruff `I002`.
- Data crossing a module boundary is a Pydantic v2 model or a frozen dataclass, never a
  raw dict.
- Reward functions are pure: no I/O, no globals, deterministic.
- Coverage floor 80%. Tightens to `rewards/`, `env/`, `eval/metrics/` at P2.
- **`tests/test_masking.py` is mandatory and blocking** from P3. Injected `<info>` tokens
  were not generated by the policy and must carry zero loss weight. Unmasked, the model
  learns to predict its own retrieval results — invisible in training curves, and it
  poisons every number downstream.

## Pipeline

| Stage | Command | Blocking |
|---|---|---|
| `lint` | `ruff check`, `ruff format --check` | yes |
| `typecheck` | `mypy --strict verisearch/` | yes |
| `unit` | `pytest -m "not gpu and not integration"`, coverage 80% | yes |
| `integration` | 5-question end-to-end, fake retriever, CPU | yes |
| `smoke-train` | 5 GRPO steps on 1.5B, asserts loss finite | nightly, `main` |
| `eval-regression` | fixed 100-example eval, F1 must not drop > 2 pts | nightly, `main` |
| `artifact` | publish coverage + eval report | `main` only |

Red pipeline blocks review. A red `main` is the top priority for both people.

Nightly stages are guarded on `scripts/02_train.sh` and `scripts/03_eval.sh` existing, so
they skip cleanly until P3 lands them.
